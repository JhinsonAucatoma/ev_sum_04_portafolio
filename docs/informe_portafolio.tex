    \subsection{Evidencia 1 --- Código propio: criterio de fragmentación horizontal}

    \noindent\textbf{Unidad del curso:} Unidad 3. Bases de Datos Distribuidas (Tema 2: Diseño y Fragmentación de Bases de Datos Distribuidas).

    \noindent\textbf{Artefacto:}
    \begin{itemize}[noitemsep,topsep=2pt]
  \item Archivo: \texttt{sql/03\_fragmentacion\_horizontal.sql}
  \item Commit: \texttt{1640a76} (hash completo: \texttt{1640a76d196694c66c4961684013548ba3780fe6})
  \item Repositorio: \url{https://github.com/JhinsonAucatoma/practica-fragmentacion}
    \end{itemize}

    \begin{lstlisting}[caption={Fragmento de \texttt{03\_fragmentacion\_horizontal.sql}: esquema del fragmento horizontal de \texttt{pedidos}.}, label={lst:ev1-horizontal}]
CREATE TABLE pedidos_fragmento (
    pedido_id INTEGER PRIMARY KEY,
    cliente_id INTEGER NOT NULL,
    producto_id INTEGER NOT NULL,
    fecha DATE NOT NULL,
    monto NUMERIC(8,2) NOT NULL,
    sede VARCHAR(20) NOT NULL
);
    \end{lstlisting}

    \noindent\textbf{Explicación del aprendizaje.}
    Al diseñar el esquema de fragmentación horizontal de la tabla \texttt{pedidos} (Listado~\ref{lst:ev1-horizontal})
    evalué dos criterios de corte posibles: por \texttt{sede} o por \texttt{producto\_id}. Descarté \texttt{producto\_id}
    porque las consultas típicas del escenario (una cafetería con tres sedes) son del tipo ``ventas de esta sede'', no ``ventas de este producto'';
    fragmentar por producto no habría acercado los datos a quien los consulta. Entonces opté por \texttt{sede} porque ese criterio hace que cada
    fragmento resida físicamente cerca de los usuarios que más lo consultan, lo que en \emph{Principles of Distributed Database Systems} se plantea
    como uno de los objetivos centrales del diseño de fragmentación: minimizar el costo de las consultas más frecuentes acercando los datos a su patrón
    de acceso~\cite{ozsu2020principles}. Lo que aprendí es que una decisión de fragmentación no se valida solo verificando que sea correcta en abstracto
    (completitud, reconstrucción, disjunción), sino evaluando si el criterio de corte refleja cómo se va a consultar el dato en la práctica; dos esquemas
    igualmente correctos pueden tener rendimientos muy distintos según ese ajuste.

    \subsection{Evidencia 2 --- Análisis técnico: verificación cuantitativa de consistencia}

    \noindent\textbf{Unidad del curso:} Unidad 3. Bases de Datos Distribuidas (Tema 2: Diseño y Fragmentación de Bases de Datos Distribuidas).

    \noindent\textbf{Artefacto:}
    \begin{itemize}[noitemsep,topsep=2pt]
  \item Archivo: \texttt{sql/07\_verificacion.sql}
  \item Commit: \texttt{1640a76} (hash completo: \texttt{1640a76d196694c66c4961684013548ba3780fe6})
  \item Repositorio: \url{https://github.com/JhinsonAucatoma/practica-fragmentacion}
    \end{itemize}

    \begin{lstlisting}[caption={Consultas de \texttt{07\_verificacion.sql} usadas para medir completitud, reconstrucción y disjunción.}, label={lst:ev2-verificacion}]
-- 1) COMPLETITUD
SELECT COUNT(*) AS filas_globales FROM pedidos_global;
SELECT COUNT(*) AS filas_centralizadas FROM pedidos;

-- 2) RECONSTRUCCION
SELECT sede, SUM(monto) AS total_global
FROM pedidos_global GROUP BY sede ORDER BY sede;
SELECT sede, SUM(monto) AS total_centralizado
FROM pedidos GROUP BY sede ORDER BY sede;

-- 3) DISJUNCION
SELECT pedido_id, COUNT(*) AS veces
FROM pedidos_global
GROUP BY pedido_id
HAVING COUNT(*) > 1;
    \end{lstlisting}

    \noindent\textbf{Protocolo de medición.}
    Tras cargar el conjunto de prueba (6 clientes y 8 pedidos, repartidos de forma desigual entre Campus, Babahoyo y Ventanas) y construir la vista \texttt{pedidos\_global} mediante \texttt{postgres\_fdw} (unión de los tres fragmentos horizontales), ejecuté por \texttt{psql} dentro del contenedor \texttt{pg-campus} las tres consultas del Listado~\ref{lst:ev2-verificacion} y comparé cada resultado contra la tabla \texttt{pedidos} de ese mismo nodo, que conservé sin fragmentar como referencia central (Tabla~\ref{tab:ev2-resultados}).

    \noindent\textbf{Interpretación.}
    Los tres resultados confirman, con datos medidos por mí, las tres condiciones de corrección que exige toda fragmentación correcta según
    la literatura del curso: completitud (ningún dato se perdió: 8 filas en ambas consultas), reconstrucción (\texttt{UNION ALL} reproduce
    exactamente los mismos totales por sede que la tabla centralizada) y disjunción (ningún \texttt{pedido\_id} aparece en más de un fragmento)~\cite{ozsu2020principles}.
    Sin embargo, esta verificación tiene una limitación que no debo presentar como concluyente: se ejecutó sobre un conjunto sintético de solo 8 filas, en un único punto
    en el tiempo y sin escritura concurrente entre nodos. No comprueba, por ejemplo, qué pasaría si dos sedes insertaran pedidos simultáneamente mientras otro cliente
    consulta \texttt{pedidos\_global} un escenario donde los compromisos entre disponibilidad, latencia y consistencia que describe el modelo PACELC sí serían relevantes y
    podrían mostrar inconsistencias transitorias que esta prueba estática, de un solo escritor, no puede detectar~\cite{abadi2012pacelc}. Lo que aprendí es que verificar
    completitud/reconstrucción/disjunción sobre datos estáticos prueba la corrección del \emph{esquema} de fragmentación, pero no sustituye una prueba de consistencia bajo
    concurrencia real.

    \subsection{Evidencia 3 --- Reflexión documentada: de un fallo total a una degradación controlada}

    \noindent\textbf{Unidad del curso:} Unidad 2. Aplicaciones Distribuidas: fragmentación horizontal, transparencia de ubicación y autonomía local (caso Banco del Austro).

    \noindent\textbf{Artefacto:}
    \begin{itemize}[noitemsep,topsep=2pt]
  \item Archivo: \texttt{service/ConsultaDistribuidaService.java}
  \item Método: \texttt{listarTodosLosClientes}
  \item Commit: \texttt{e8e57ee} (hash completo: \texttt{e8e57eed14cefa94762c28db9d5884c0b2bbcaf2})
    \end{itemize}
    \noindent Repositorio: {\footnotesize\url{https://github.com/JhinsonAucatoma/TA_IND_02_Analisis_Consistencia_Replicacion_BDD}}

    \noindent\textbf{El hecho concreto.}
    Al detener el contenedor \texttt{banco-quito} para probar la tolerancia a fallos, la versión original de \texttt{listarTodosLosClientes()} (que simplemente concatenaba las consultas de los dos \texttt{JdbcTemplate} (\texttt{jdbcCuenca} y \texttt{jdbcQuito}) sin ningún manejo de errores) respondió con un error 500 Internal Server Error, incluso para los clientes de Cuenca, cuyo nodo seguía activo. La versión corregida quedó así:

    \begin{lstlisting}[style=javastyle, caption={Fragmento de \texttt{listarTodosLosClientes} con manejo de fallos por nodo.}, label={lst:ev3-fallback}]
try { union.addAll(jdbcCuenca.queryForList(sql)); }
catch (Exception e) { nodosCaidos.add("CUENCA"); }

try { union.addAll(jdbcQuito.queryForList(sql)); }
catch (Exception e) { nodosCaidos.add("QUITO"); }

Map<String, Object> resultado = new HashMap<>();
resultado.put("clientes", union);
resultado.put("totalDisponibles", union.size());
if (!nodosCaidos.isEmpty()) {
    resultado.put("advertencia",
        "Los siguientes nodos no respondieron y se excluyeron de la union: " + nodosCaidos);
    resultado.put("nodosCaidos", nodosCaidos);
}
    \end{lstlisting}

    \noindent\textbf{Reflexión.}
    El supuesto que resultó falso fue asumir, de forma implícita, que todos los nodos consultados en una operación distribuida iban a responder siempre. En el código original
    ese supuesto ni siquiera estaba escrito (simplemente no había ningún \texttt{try/catch}) lo cual es precisamente lo peligroso: un supuesto no declarado es más difícil de
    cuestionar que uno explícito. La caída de un único nodo (Quito) bastó para tumbar una respuesta que, en un 60\,\% de los casos (los clientes de Cuenca), sí se podía entregar.
    Al envolver cada consulta por nodo en su propio \texttt{try/catch} (Listado~\ref{lst:ev3-fallback}), cambié la decisión de diseño: en lugar de exigir que \emph{todos} los nodos
    respondan para dar cualquier respuesta, el sistema ahora entrega lo que sí tiene disponible junto con una advertencia explícita de qué nodos faltaron. Es una versión artesanal
    del patrón \emph{Circuit Breaker} que describe Nygard para sistemas en producción: preferir una degradación visible y controlada antes que una falla total o, peor, una respuesta
    silenciosamente incompleta~\cite{nygard2018releaseit}. Lo que me llevo de esto, más allá de este proyecto puntual, es que en cualquier operación que dependa de múltiples nodos remotos
    debo preguntarme explícitamente ``¿qué debe devolver este endpoint si uno de los nodos no responde?'' \emph{antes} de escribir el código de integración, no después de que una prueba
    e caída lo revele por accidente.
